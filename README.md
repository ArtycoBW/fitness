# Страйд

Веб-система управления фитнес-клубом: публичный сайт, кабинет клиента, рабочее место тренера и управление клубом.

## Возможности

- Клиенты, тренеры, залы, направления тренировок, фотографии, рабочие часы и периоды недоступности.
- Версии тарифов, покупки, абонементы, заморозки, остатки посещений и неизменяемый журнал движений.
- Разовые и повторяющиеся занятия, проверка пересечений, запись, очередь ожидания, отмена и отметка посещения.
- Оплата картой, Альфа Pay, Яндекс Pay и Сбер Pay; наличные и терминал на стойке; подтверждения с читаемым Code128 и частичные/полные возвраты.
- Конструктор программ, библиотека упражнений, опубликованные версии, назначения, подходы, результаты и комментарии тренера.
- Уведомления, предпочтения доставки, напоминания, обращения с сайта, отчёты, CSV, настройки клуба и аудит изменений.
- Адаптивный лендинг с Stride Nine, композициями GetLayers, сценой залов Three.js, управлением движением и альтернативой без WebGL.

Платёжный провайдер является внутренним имитатором: реальные банковские операции не выполняются. Сервер получает выбранный способ и последние четыре цифры карты; полный номер и CVV не передаются и не сохраняются. Подтверждение операции — внутренний документ клуба, не фискальный чек. Для подключения настоящего эквайринга потребуется отдельный провайдер, его SDK/токенизация и обработка подписанных уведомлений.

## Архитектура

| Часть               | Состав                                                                                        |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `apps/web`          | Next.js App Router, React, TypeScript, Tailwind, shadcn/Radix, TanStack Query, GSAP, Three.js |
| `apps/api`          | NestJS, Prisma, PostgreSQL, отдельный worker                                                  |
| `prisma/migrations` | Схема, индексы, ограничения пересечений GiST, защита неизменяемой истории                     |
| `tests`             | PostgreSQL integration, Playwright, axe, воспроизводимый нагрузочный сценарий                 |
| `infra`             | Dockerfile приложений и Caddy для HTTPS                                                       |

Деньги хранятся целыми копейками, время — в UTC, интерфейс клуба использует `Europe/Moscow`. Роли `OWNER`, `ADMIN`, `RECEPTION`, `TRAINER`, `CLIENT` проверяются сервером, включая принадлежность данных. Конкурентные записи и финансовые операции используют транзакции, блокировки и ключи идемпотентности. Изменение опубликованного тарифа или программы создаёт новую версию.

Сессии имеют абсолютный срок 7 дней и ограничение бездействия 24 часа. Cookie сессии — HttpOnly; изменяющие запросы проверяют Origin и CSRF. Пароли хешируются Argon2. Письма в outbox зашифрованы; worker независимо обрабатывает доставку, платежи, записи, напоминания, экспорты и очистку файлов. Доставка SMTP допускает повтор при сбое между отправкой письма и фиксацией результата.

## Требования и установка

Node.js 24 LTS, pnpm 11.8.0 и PostgreSQL 18. Docker с Linux-контейнерами удобен для инфраструктуры, но приложение работает и с установленным PostgreSQL. Зафиксированные зависимости находятся в `pnpm-lock.yaml`.

```sh
corepack enable
corepack prepare pnpm@11.8.0 --activate
pnpm install --frozen-lockfile
```

Скопируйте `.env.example` в `.env`. Задайте случайный `OUTBOX_SECRET` длиной не менее 32 символов, например результат `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`. Этот ключ нужно сохранять вместе с резервными копиями: его замена делает ожидающие письма нечитаемыми.

```sh
pnpm infra:up
pnpm db:generate
pnpm db:migrate
pnpm dev
```

В отдельном терминале запустите `pnpm --filter @fitness/api worker`. Без worker асинхронные операции остаются в очереди. При собственной установке PostgreSQL вместо `infra:up` создайте базу, укажите `DATABASE_URL` и разрешите миграциям установку `btree_gist`.

Адреса локального окружения:

| Сервис                      | Адрес                                     |
| --------------------------- | ----------------------------------------- |
| Сайт                        | http://localhost:3000                     |
| API                         | http://localhost:4000/api/v1              |
| OpenAPI, только development | http://localhost:4000/api/docs            |
| Mailpit                     | http://localhost:8025                     |
| Готовность API и БД         | http://localhost:4000/api/v1/health/ready |

## Первый вход и данные

Для пустого клуба задайте переменные `OWNER_EMAIL`, `OWNER_PASSWORD` (не менее 12 символов), при необходимости `OWNER_NAME`, затем выполните `pnpm --filter @fitness/api owner:create`. Команда не заменяет существующего руководителя. Через управление сотрудниками руководитель приглашает администраторов, сотрудников стойки и тренеров. Клиенты могут зарегистрироваться на сайте.

Для локального знакомства задайте `SEED_PASSWORD` (не менее 12 символов) и выполните `pnpm db:seed`. Команда создаёт вымышленные профили, каталог, тарифы, расписание на две недели и программу тренировок. Повторный seed сохраняет историю и существующие пароли; в production он запрещён.

| Аккаунт                  | Роль         |
| ------------------------ | ------------ |
| `owner@stride.local`     | Руководитель |
| `reception@stride.local` | Стойка       |
| `trainer@stride.local`   | Тренер       |
| `client@stride.local`    | Клиент       |

Пароль всех новых seed-аккаунтов берётся из `SEED_PASSWORD`. Письма регистрации и приглашений в локальном окружении доступны в Mailpit. Перед внешним размещением заполните реальные контакты, адрес и реквизиты клуба в настройках и согласуйте тексты пользовательских документов.

## Переменные окружения

| Переменная                            | Назначение                                                                             |
| ------------------------------------- | -------------------------------------------------------------------------------------- |
| `DATABASE_URL`                        | PostgreSQL URL; специальные символы пароля должны быть URL-кодированы                  |
| `WEB_URL`                             | Полный origin сайта, без подкаталога; проверка Origin и ссылки в письмах               |
| `API_URL`                             | Адрес NestJS для Next.js; применяется при сборке proxy и в серверных запросах          |
| `SITE_URL`                            | Публичный адрес сайта для метаданных и sitemap                                         |
| `API_PORT`                            | Порт API, по умолчанию 4000                                                            |
| `OUTBOX_SECRET`                       | Постоянный секрет шифрования очереди писем, минимум 32 символа                         |
| `UPLOADS_DIR`                         | Общий каталог API и worker; для нативного запуска удобен абсолютный путь               |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM` | SMTP сервер, порт, адрес отправителя                                                   |
| `SMTP_SECURE`                         | `true` для implicit TLS, обычно порт 465                                               |
| `SMTP_REQUIRE_TLS`                    | `true` для обязательного STARTTLS, обычно порт 587                                     |
| `SMTP_USER`, `SMTP_PASSWORD`          | Указываются вместе, для локального Mailpit не нужны                                    |
| `TRUST_PROXY_HOPS`                    | По умолчанию 0; 1 только за доверенным reverse proxy при закрытом прямом доступе к API |
| `POSTGRES_PASSWORD`                   | Пароль PostgreSQL в Compose                                                            |
| `PAYMENT_PROVIDER`                    | `simulator`, единственный реализованный адаптер                                        |

Cookie становится Secure при HTTPS в `WEB_URL`. Не устанавливайте доверие ко всем proxy: поддельный адрес клиента иначе позволит обходить ограничения частоты запросов. Caddy направляет `/api/v1/*` непосредственно в NestJS и формирует forwarded-заголовки. Для локальной разработки запросы браузера проходят через rewrite Next.js.

## Production-запуск

Нативный запуск из корня проекта после миграций:

```sh
pnpm build
```

Запустите три процесса: `NODE_ENV=production node apps/api/dist/main.js`, `NODE_ENV=production node apps/api/dist/worker.js` и `pnpm --filter @fitness/web start`. В PowerShell переменная задаётся отдельно: `$env:NODE_ENV='production'`. Менеджер процессов должен перезапускать API/worker/web после аварийного завершения. Изменение `API_URL` или `SITE_URL` требует пересборки web.

Для полного Compose-окружения установите в `.env` `SMTP_HOST=mailpit`, если используете входящий в проект Mailpit, и задайте секреты:

```sh
docker compose --profile app config --quiet
docker compose --profile app up -d --build
docker compose --profile app ps
docker compose logs --tail=100 api worker web
```

Сервис `migrate` завершает миграции до запуска приложений. API и worker используют общий volume `uploads`. БД, API, web и интерфейс Mailpit привязаны к loopback хоста. Для первого руководителя в контейнере передайте `OWNER_EMAIL` и `OWNER_PASSWORD` в `docker compose --profile app run --rm -e OWNER_EMAIL -e OWNER_PASSWORD api node apps/api/dist/bootstrap-owner.js`.

Для сервера с доменом задайте `SITE_DOMAIN=club.example`, `WEB_URL=https://club.example`, `TRUST_PROXY_HOPS=1`, внешний SMTP и надёжные секреты. DNS должен указывать на сервер, порты 80/443 — быть доступны. Затем:

```sh
docker compose --profile app --profile edge up -d --build
```

Caddy получает и обновляет TLS-сертификат. Образы приложений запускаются от пользователя `node`. Для планового обновления сохраните резервную копию, соберите новую версию, примените миграции и проверьте readiness. Главная и списки публичного каталога рендерятся сервером при запросе: сборка образа не фиксирует пустой каталог, когда API ещё не запущен. Данные страниц отдельных объектов могут кэшироваться на 60 секунд.

Внешнее размещение требует собственного сервера и домена; репозиторий не создаёт их автоматически.

## Резервное копирование и восстановление

Нужны `pg_dump` и `pg_restore` версии PostgreSQL 18 в PATH либо `PG_BIN` с путём к их каталогу.

```sh
node scripts/database.cjs backup backups/club-2026-09-13.dump
```

Команда создаёт custom-format dump и файл `.sha256`, не перезаписывая существующую копию. Для восстановления задайте `RESTORE_DATABASE_URL` с именем **новой** базы, например `fitness_restored`, затем:

```sh
node scripts/database.cjs restore backups/club-2026-09-13.dump
```

Скрипт проверяет checksum, отказывается заменять существующую базу и восстанавливает в одной транзакции. После этого проверьте `pnpm db:migrate`, readiness, суммы платежей и возвратов, баланс посещений и доступность загруженных изображений. Только после проверки переключайте рабочий `DATABASE_URL`.

Отдельно сохраняйте `UPLOADS_DIR`/volume `uploads`, `.env` и `OUTBOX_SECRET` в защищённом хранилище. Для согласованной копии БД и файлов остановите изменяющие запросы и worker на время снимка. Сам dump PostgreSQL согласован транзакционно, но не содержит файлов. Рекомендуемый график: ежедневная копия, хранение 7 ежедневных и 4 недельных копий, ежемесячная проверка восстановления. Частота определяется допустимой потерей данных клуба.

## Проверки

```sh
pnpm lint
pnpm typecheck
pnpm build
pnpm test
```

Интеграционные тесты запускают собранный API на порту 4100. Runner создаёт отдельную базу с суффиксом `_test` и применяет все миграции. Можно указать `TEST_DATABASE_URL` на заранее подготовленную базу. Не запускайте два таких прогона одновременно на одном порту.

Для браузерных проверок нужны запущенные web, API и worker с вымышленными seed-данными. Задайте `E2E_CLIENT_EMAIL`, `E2E_OWNER_EMAIL`, `E2E_TRAINER_EMAIL`, `E2E_PASSWORD` и выполните:

```sh
pnpm exec playwright install chromium
pnpm test:e2e
```

`CHROME_PATH` выбирает установленный Chrome, `E2E_BASE_URL` меняет адрес web. Проверки создают настоящие записи внутри приложения: покупки, возвраты, назначения и обращения. Используйте отдельную базу. Набор включает четыре роли, мобильное меню, покупку всеми четырьмя способами, независимое чтение Code128, запись и отмену, программу от тренера до результата клиента, отчёты и axe-аудит. CI выполняет lint, типы, сборку, PostgreSQL-тесты и Playwright на production-процессах.

Нагрузочный сценарий использует отдельную восстановленную seed-базу с совершённой покупкой. Задайте `LOAD_DATABASE_URL` с новым именем, заканчивающимся `_load_test`, и `LOAD_TEMPLATE_DATABASE` с именем восстановленной базы, затем `node tests/performance/seed.cjs`. Он добавляет 10 000 клиентов, 50 000 исторических занятий, 100 000 отменённых записей и 50 000 оплат. Это синтетический объём для проверки запросов, не имитация распределения реального клуба.

Запустите отдельный API на порту 4101 с этой базой, задайте `E2E_PASSWORD` от seed-руководителя и выполните `node tests/performance/run.cjs`. По умолчанию 30 запросов/сек в течение 300 секунд: 90% чтения списков/карточек/расписания и 10% добавления заметок. Отчёт сохраняется в `.local/load-report.json`; проверяются p95 чтения ≤500 мс и записи ≤800 мс. Параметры `LOAD_SECONDS`, `LOAD_RATE`, `LOAD_REPORT`, `LOAD_FIXTURE_OUTPUT` позволяют повторить измерения. Сценарий ограничен localhost; результаты нужно повторно измерить на целевом сервере.

## Файлы и эксплуатация

Изображения JPG/PNG/WebP ограничены 5 МБ и 20 млн пикселей, перекодируются в WebP без исходных метаданных. Неиспользуемые изображения удаляются через 7 дней, выгрузки доступны автору 24 часа и повторно проверяют его права. CSV экранирует формулы. Логи не должны содержать пароли, cookie, платёжные реквизиты или содержимое писем.

Следите за `/health/ready`, журналом ошибок worker, необработанными письмами в разделе доставки, очередью экспортов, свободным местом и резервными копиями. Письма с исчерпанными попытками можно повторить из интерфейса руководителя. При остановке worker данные очереди остаются в PostgreSQL, обработка продолжается после запуска.

ТЗ, инструкции агентов, исходные архивы, локальные отчёты и секреты исключены из Git. Происхождение визуальных материалов описано в `licenses/`.
